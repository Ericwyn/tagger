# Tagger 前期设计文档

> 调研与设计基线：2026-08-20

## 1. 项目定位

Tagger 是一个使用 Go 实现的自托管音乐元数据管理工具。它直接读取服务器或 NAS 上的音乐目录，在浏览器中查看、检索、编辑并批量补全音频标签。

首个正式版本聚焦两项核心能力：

1. 浏览和编辑音乐文件，首批认证支持 MP3、FLAC、WAV。
2. 通过可替换的抓取策略，从 MusicBrainz、Apple Music、网易云、酷我等来源查询歌曲、专辑、歌手、歌词、封面、音轨号和光盘号，再由用户确认后写回文件。

项目采用前后端一体化部署：前端单独开发和构建，生产构建产物嵌入 Go 可执行文件，最终只需分发一个二进制文件。运行时仍会在数据目录保存 SQLite、缓存、日志和历史记录；“单二进制”不等于“无运行时数据目录”。

## 2. 已确定的关键决策

| 主题 | 决策 |
|---|---|
| 前端 | 参考本地 `/home/ericwyn/dev/agent/chattor/frontend`，使用 React 19、TypeScript、Vite、Tailwind CSS 4、Lucide |
| 前后端关系 | 同源 API；生产环境将 `frontend/dist` 复制到 `web/dist` 并用 `go:embed` 嵌入 |
| Go Web 层 | 优先使用 Hertz，与本地 Chattor 的组织方式保持一致 |
| 元数据引擎 | 以 `go.senan.xyz/taglib` 为首选，封装在自有 `TagEngine` 接口后 |
| 本地数据库 | SQLite + `modernc.org/sqlite`，保持 CGO-free 和单进程部署 |
| 后台任务 | SQLite 持久化任务队列 + 进程内 worker，不引入 Redis/Celery |
| 文件安全 | 只接收 `library_id + relative_path/file_id`，禁止 API 直接操作任意绝对路径 |
| 写入策略 | 同目录临时副本写入、写后重读校验、原子替换、标签历史；默认保留未知标签 |
| 批量操作 | 必须先生成差异预览，再确认执行；自动匹配默认不自动写文件 |
| 抓取器 | 能力型策略接口、注册表、来源级限流/缓存/熔断；非官方来源默认标记为实验性 |
| 指纹识别 | 非 MVP；Chromaprint/fpcalc 作为可选增强，不影响核心单二进制运行 |

## 4. 一句话架构

浏览器中的 React SPA 通过同源 REST API 和 SSE 与 Go 服务通信；Go 服务用 SQLite 保存曲库索引、任务、抓取缓存和修改历史，用 TagLib-WASM 读写音乐文件，并通过一组互相隔离的数据源策略补全元数据。

## 5. 术语

- **文件**：磁盘上的一个音频文件，身份由数据库 ID 表示，路径只是它的当前属性。
- **曲目**：从文件标签归一化出的音乐语义对象。
- **标签**：实际写入音频容器的 ID3、Vorbis Comment、RIFF INFO 等字段。
- **元数据**：应用层的统一字段，包括标签、技术属性和外部来源信息。
- **候选项**：抓取器返回、尚未写入本地文件的一组外部元数据。
- **修订**：一次文件标签变更前后的快照和审计记录。
- **认证支持**：经过测试样本、写后校验和至少一个独立工具互操作验证的格式；不等同于底层库声称可打开该格式。
