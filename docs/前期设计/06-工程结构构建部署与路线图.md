# 工程结构、构建部署与路线图

## 1. 推荐目录

```text
.
├── cmd/
│   └── tagger/
│       └── main.go
├── internal/
│   ├── app/                 # 组装依赖、生命周期
│   ├── auth/                # setup、session、CSRF
│   ├── config/              # flags/env/settings
│   ├── domain/              # 领域类型与错误
│   ├── filewrite/           # 安全写入、锁、恢复
│   ├── jobs/                # SQLite queue、worker、events
│   ├── library/             # 曲库/目录/文件服务
│   ├── scanner/             # discover/diff/extract/persist
│   ├── matching/            # normalize、score、merge
│   ├── providers/
│   │   ├── registry.go
│   │   ├── musicbrainz/
│   │   ├── coverartarchive/
│   │   ├── lrclib/
│   │   ├── applemusic/
│   │   ├── itunes/
│   │   ├── netease/
│   │   └── kuwo/
│   ├── server/              # Hertz handlers/middleware
│   ├── store/               # SQLite repositories
│   │   └── migrations/
│   └── tags/
│       ├── engine.go
│       └── taglibwasm/
├── frontend/                # React + TS + Vite + Tailwind
├── web/
│   ├── embed.go
│   └── dist/
│       └── .gitkeep
├── testdata/
│   └── audio/               # 小型、许可证清晰的格式语料
├── scripts/                 # 开发/发布辅助，非运行依赖
├── docs/
│   └── 前期设计/
├── Makefile
├── go.mod
└── README.md
```

分包规则：

- `internal/domain` 不依赖 Hertz、SQLite 或 TagLib。
- handler 只做认证、DTO 和错误映射。
- repository 不做文件 I/O。
- provider 不调用 file writer。
- matching 不直接发 HTTP，通过 provider 接口获取候选。
- file writer 只接受已经解析并授权的 FileRef。
- 循环依赖通过小接口和 app 组装解决，不创建 `utils` 垃圾包。

## 3. 静态资源嵌入

`web/embed.go`：

```go
package web

import (
    "embed"
    "io/fs"
)

//go:embed all:dist
var embedded embed.FS

func Dist() fs.FS {
    sub, err := fs.Sub(embedded, "dist")
    if err != nil {
        panic(err)
    }
    return sub
}
```

使用 `all:dist` 确保空仓库中的 placeholder 也可被嵌入。正式构建前必须检查 `web/dist/index.html`，不能把只有 `.gitkeep` 的开发二进制误当成发布物。

服务资源时：

- `http.FileServer(http.FS(web.Dist()))` 或 Hertz 对等实现。
- `/assets/<hash>.*` 设置 `Cache-Control: public, max-age=31536000, immutable`。
- `index.html` 设置 `no-cache`。
- Content-Type 使用标准 MIME 探测，不手写只覆盖少数后缀的 switch。
- SPA fallback 排除 API/health/assets，并仅响应 HTML GET。

## 4. Makefile

参考 Chattor 后建议：

```makefile
.PHONY: all build build-frontend dev-backend dev-frontend \
        test test-go test-frontend lint clean

BINARY ?= tagger
VERSION ?= dev

all: build

build-frontend:
	cd frontend && npm ci && npm run build
	rm -rf web/dist
	cp -r frontend/dist web/dist

build: build-frontend
	CGO_ENABLED=0 go build -trimpath \
		-ldflags "-X main.version=$(VERSION)" \
		-o dist/$(BINARY) ./cmd/tagger

dev-backend:
	TAGGER_DEV_MODE=true go run ./cmd/tagger

dev-frontend:
	cd frontend && npm run dev

test: test-go test-frontend

test-go:
	go test ./...

test-frontend:
	cd frontend && npm test

lint:
	go vet ./...
	cd frontend && npm run lint

clean:
	rm -rf dist frontend/dist web/dist
	mkdir -p web/dist
	touch web/dist/.gitkeep
```

实际落地时优化：

- `main.version` 最好放到稳定包路径，如 `internal/version.Version`。
- build 应先创建 `dist/`。
- CI 使用固定 Node/npm/Go 版本。
- 发布使用 `-s -w` 前先确认调试和符号需求。
- `npm ci` 依赖提交 lockfile。
- clean 的删除目标必须保持为明确的仓库子目录。

## 5. 开发方式

两个终端：

```bash
make dev-backend   # 127.0.0.1:8080
make dev-frontend  # 127.0.0.1:3000
```

Vite：

- `/api`、`/healthz`、`/readyz` 代理到 Go。
- 浏览器打开 3000，HMR 正常。
- API client 使用相对 URL，生产无需修改 base URL。

后端开发模式可以选择把非 API 请求 reverse proxy 到 Vite，这样开发和生产都访问 8080；但必须正确支持 query、headers、status、stream 和 WebSocket upgrade。若暂时不实现，直接打开 Vite 端口更清晰。

## 6. 生产运行

### 6.1 本机

```bash
./tagger \
  --listen 127.0.0.1:8080 \
  --data-dir /var/lib/tagger
```

第一次通过 UI 添加音乐目录。也可以提供：

```bash
./tagger library add --name Music --path /mnt/music --read-only
```

CLI 是否进入 MVP 由迭代时间决定，但启动 flags 和 `doctor` 很有价值。

### 6.2 Docker

容器仍只有一个应用进程：

```yaml
services:
  tagger:
    image: example/tagger:latest
    ports:
      - "127.0.0.1:8080:8080"
    volumes:
      - /path/to/music:/music:rw
      - /path/to/tagger-data:/data:rw
    environment:
      TAGGER_LISTEN: 0.0.0.0:8080
      TAGGER_DATA_DIR: /data
    restart: unless-stopped
```

建议：

- 镜像使用 non-root 用户。
- 容器 UID/GID 与 NAS 文件权限匹配。
- 音乐目录可先挂载 `:ro` 完成试扫，再改 `:rw`。
- 数据目录与音乐目录分开备份。
- 对外访问放在 HTTPS reverse proxy 后。
- 不提供默认密码。

### 6.3 单二进制的边界

二进制包含：

- Go server。
- SQLite driver。
- 数据库 migration。
- TagLib-WASM。
- React 生产静态资源。

不包含：

- Node/npm（只用于构建）。
- FFmpeg/fpcalc（可选增强）。
- 用户音乐、SQLite、缓存、历史 blob。

## 7. CI

Pull Request：

1. `go test ./...`。
2. `go vet ./...` 和 lint。
3. 前端 typecheck/lint/unit test。
4. 前端 production build。
5. `CGO_ENABLED=0 go build`。
6. API contract diff。
7. 小型音频语料读写/重读测试。
8. path traversal、symlink、图片 bomb 和认证测试。

主分支/发布：

1. Linux amd64/arm64 构建。
2. macOS/Windows 按正式支持矩阵构建。
3. 独立工具互操作测试镜像。
4. Playwright 首次设置、扫描、编辑、冲突、批量审核。
5. SBOM、依赖许可证和漏洞扫描。
6. 二进制 checksum 和可复现构建信息。

音频 fixture 必须体积小、来源和许可证明确。不要把用户音乐或网络下载样本提交到仓库。

## 8. 版本与依赖策略

- Go module 和 npm lockfile 都提交。
- go-taglib 固定明确版本/commit；升级必须跑完整格式语料。
- TagLib-WASM 版本显示在系统诊断中。
- provider adapter 有独立 schema version，远程响应变化不要求整体 DB migration。
- 不自动追随数据源项目的 main/master。
- 依赖升级与格式写入行为变化分开 PR，便于回归定位。
- 记录 LGPL/MPL/AGPL 等依赖边界和分发义务；尤其检查 go-taglib/内嵌 TagLib-WASM 的 LGPL/MPL 分发要求。设计参考不等于代码依赖。

## 9. 分阶段路线图

### Phase 0：脚手架与风险验证

目标：

- 初始化 Go/React 工程。
- 完成 Chattor 式 build/embed。
- 接入 SQLite migration。
- 用 go-taglib 对 MP3/FLAC/WAV 样本完成读、写、封面、重读 spike。
- 验证 Linux amd64/arm64 CGO-free。

退出条件：

- `make build` 生成可启动单二进制。
- 兼容性 spike 形成报告，决定 MP3 写入版本和 WAV policy。

### Phase 1：只读曲库

目标：

- 首次设置、认证、library root。
- full/quick scan、目录和曲目列表。
- 标签、技术属性、封面、歌词读取。
- Range 试听、解析失败和任务进度。

退出条件：

- 5 万文件规模模拟测试。
- NFS/SMB 无 watcher 时可手动/定时对账。
- 任意路径逃逸测试通过。

### Phase 2：安全编辑

目标：

- 统一 patch。
- 单曲编辑和 diff。
- 临时副本、原子替换、重读验证。
- revision conflict、历史和恢复。
- 批量手工编辑。

退出条件：

- MP3/FLAC 认证 A；WAV 达到明确的 A/B 结论。
- 故障注入下不破坏原文件。
- 外部编辑冲突可复现并正确返回 409。

### Phase 3：开放数据源

目标：

- provider registry。
- MusicBrainz、CAA、LRCLIB。
- 多源搜索 UI、字段 diff、provenance。
- 限流、缓存、重试和 provider health。

退出条件：

- 单源失败不影响其他结果。
- MusicBrainz 1 request/sec、LRCLIB Retry-After 测试通过。
- 候选应用仍走 Phase 2 安全写入。

### Phase 4：中国平台与 Apple

目标：

- Apple Music token/config/storefront。
- iTunes fallback 与 UsagePolicy。
- 网易云、酷我 experimental adapter。
- 专辑匹配和批量 review。

退出条件：

- provider fixture/golden test。
- token/cookie 脱敏测试。
- 高置信批量接受仍需要总确认。

### Phase 5：强化与扩格式

候选：

- M4A/OGG/Opus/APE/WV/AIFF/WMA/DSF 写入认证。
- 可选 Chromaprint/fpcalc。
- 文件整理/重命名预览。
- 导入/导出规则模板。
- 多用户 ACL。

每个格式单独通过读写和播放器互操作矩阵，不因 TagLib 声称支持而一次性开放。

## 10. 首批实现任务拆分

建议以可审查的小 PR 推进：

1. `chore/scaffold`：Go module、frontend、Makefile、embed、health。
2. `feat/sqlite-store`：migration、config、data-dir lock。
3. `feat/tag-engine-read`：统一模型和 TagLib 只读。
4. `feat/library-scan`：scan job、files/tracks 表。
5. `feat/library-ui`：目录、曲目表、检查器。
6. `feat/audio-artwork`：Range 与缩略图。
7. `feat/safe-writer`：patch、临时副本、验证。
8. `feat/edit-ui`：表单、diff、revision conflict。
9. `feat/history`：revision 和恢复。
10. `feat/provider-core`：registry、HTTP policy、cache。
11. `feat/musicbrainz-lrclib`。
12. `feat/batch-review`。

不要在第一个 PR 同时加入三种 provider、批量写入和格式扩展；文件安全层必须先稳定。

## 11. 风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| go-taglib 新、Navidrome 使用 fork | 核心读写行为变化 | 自有接口、固定版本、fixture、可替换 engine |
| WAV 标签不统一 | 写入后部分播放器不可见 | B 级提示、互操作矩阵、profile |
| NAS 原子性/mtime/watcher 差异 | 漏扫描或恢复复杂 | polling 对账、临时同目录、目标 NAS 测试 |
| 非官方来源频繁失效 | 批量任务失败 | Experimental、fixture、健康/隔离、开放源兜底 |
| 自动匹配误写 | 大规模错误标签 | review_required、字段 diff、默认 missing_only |
| 大封面/损坏文件耗尽资源 | DoS/崩溃 | 大小/像素/并发限制、单文件错误隔离 |
| 多进程或外部编辑冲突 | 覆盖他人修改 | data lock、per-file lock、revision |
| 标签历史被误认为完整备份 | 无法位级恢复 | UI 明示、可选完整备份、建议 NAS 快照 |
| Apple/iTunes 内容条款 | 不当持久化封面 | UsagePolicy、默认禁止 iTunes promo art 写入 |
| 数据库与文件成功边界 | 显示与磁盘不一致 | planned/committed revision、启动对账 |

## 12. 架构决策记录建议

正式开发时在 `docs/adr/` 建立 ADR：

- ADR-001：单进程、SQLite、嵌入前端。
- ADR-002：TagLib-WASM 作为首选 TagEngine。
- ADR-003：文件写入使用临时副本和原子替换。
- ADR-004：provider 使用能力型编译期策略。
- ADR-005：任务使用 SQLite lease queue。
- ADR-006：同步歌词 MVP 采用 sidecar 兼容策略。
- ADR-007：非官方 provider 默认 Experimental。

当 spike 结果推翻某个假设时更新 ADR，而不是只改代码。

## 13. 开始编码前的最后检查

1. 选定项目 module path 和许可证。
2. 创建/获得可分发的 MP3、FLAC、WAV 测试样本。
3. 在目标 NAS 文件系统上验证 copy/fsync/rename。
4. 确认 MP3 默认写入版本。
5. 确认 WAV 目标播放器和支持等级。
6. 明确 Apple Music 开发者凭据是否可用。
7. 明确网易云/酷我是否只在个人环境启用。
8. 决定完整音频备份默认关闭还是首次写入强提示。
9. 确定第一版支持的 OS/ARCH。

完成这些决策后即可进入 Phase 0，不需要先实现更多功能。
