## 2. music-tag-web 的可借鉴点

### 2.1 公开源码快照

调研时仓库 HEAD 为 `077fcc4625dc7fc9e7a1bee78ae1fcc17ad23edc`。公开源码与 README 中描述的 V2 功能并不完全处在同一技术代际：

- 后端是 Django 2.2 + Django REST Framework。
- 长任务使用 Celery；镜像还包含 worker/beat/supervisor。
- 音频标签依赖 `music-tag`/Mutagen，并在仓库中保留了格式适配代码。
- 前端是 Vue 2 + Webpack 3 + View Design/BK Magic Vue。
- 旧版界面已经形成“文件树—编辑区—搜索候选”的三栏工作台。

### 2.2 借鉴

- Web 工具最有效的信息架构仍然是高密度工作台，而不是一层层向导。
- 文件名、现有 title/artist/album 都应参与搜索。
- 多来源并发可以显著改善中文曲库的命中率。
- 歌词、封面、单曲字段应允许独立选择，而不是把候选项当成不可拆分的整体。
- 长批量任务必须展示进度和单文件结果。
- NAS/容器环境下，目录挂载、权限检测和移动端布局是产品功能，不只是部署细节。

### 2.3 不直接沿用

- 不复制其代码、图标或页面资产。该仓库 README 声明 GPLv3 并附加非商业限制，本项目应保持 clean-room 设计并单独确定许可证。
- 不采用大型 Django + Celery + 多进程依赖；本项目要求一个 Go 二进制即可启动。
- 不在 API 中传入任意绝对路径。
- 不使用大段 `if/elif` 选择数据源；改为显式策略注册表。
- 不直接修改原文件后就返回成功；必须有临时副本、重读校验和修订记录。
- 不把歌词/封面下载失败吞掉为“空值”；候选字段需要区分“没有数据”和“数据源失败”。
- 不以简单的包含关系决定批量自动写入。低置信度候选只能进入人工审核。

music-tag-web 近期公开 issue 中存在批量任务卡死、年份/日期语义和挂载目录等问题。这说明任务状态恢复、日期模型、文件系统兼容必须从第一版进入基础设计，而不能事后补救。

## 3. Navidrome 的可借鉴点

Navidrome 是播放器/媒体服务器而非标签编辑器，但其扫描器非常值得参考。当前扫描器采用多阶段流水线：

1. 扫描目录并导入新增/变更文件。
2. 处理缺失文件并尝试识别移动。
3. 刷新受影响的专辑和艺术家。
4. 导入播放列表，最后执行垃圾回收与统计刷新。

[Scanner 技术说明](https://github.com/navidrome/navidrome/blob/881073c1833e66c47839927dc3c1577e39471c25/scanner/README.md) 还体现了几个关键做法：

- 扫描由 controller 串行化，避免同一曲库并发扫描。
- 元数据读取可批处理；当前 Phase 1 每批处理 200 个文件。
- 解析阶段可并行，数据库持久化阶段保持单并发。
- 文件监听事件先合并、去重和 debounce，再触发选择性扫描。
- 扫描中断和 full scan 状态会持久化。
- 标签别名、多人艺术家拆分和日期类型由映射层处理，不散落在业务代码中。

Navidrome 的 [`mappings.yaml`](https://github.com/navidrome/navidrome/blob/881073c1833e66c47839927dc3c1577e39471c25/resources/mappings.yaml) 是本项目设计统一标签字段的重要参考。

需要注意：[fsnotify 官方说明](https://github.com/fsnotify/fsnotify) 指出 NFS、SMB 和部分 FUSE 文件系统不能可靠提供事件，且目录不会自动递归监听。因此本项目会把监听当作“加速提示”，始终保留启动扫描、定时对账和手动扫描。

## 4. Go 音频标签库结论

### 4.1 首选：go-taglib

[go-taglib](https://github.com/sentriz/go-taglib) 将 TagLib 2.1.1 编译为内嵌 WASM，并通过 wazero 运行：

- 无 CGO、无外部动态库，适合静态交叉编译和单二进制。
- 提供多值标签读写。
- 提供内嵌图片读写。
- 可读取时长、码率、位深、采样率、声道、容器和内部编码。
- README 明确列出 MP3、FLAC、M4A、WAV、OGG、WMA 等格式。
- 上游测试覆盖 MP3、FLAC、M4A、WAV、OGG 的读写和并发读取。
- Navidrome 已把它用于新的纯 Go 元数据提取路径，证明它能承担大型曲库的读取。

[TagLib 官方支持列表](https://taglib.org/) 包含 MP3、FLAC、WAV、AIFF、WavPack、Ogg/Opus、APE、MP4、ASF/WMA、DSF/DFF 等格式。其 [PropertyMap](https://taglib.org/api/p_propertymapping.html) 提供了 ID3v2、RIFF、MP4、APE、ASF 等容器之间的统一键映射。

风险与约束：

- go-taglib 项目较新，且 Navidrome 当前使用了自己的 fork/replace；必须固定版本并由自有接口隔离。
- go-taglib 采用 LGPL-2.1，内嵌的 TagLib 采用 LGPL/MPL 双许可证；发布二进制前需要完成依赖许可证清单、notice、对应源码/替换机制等合规检查。本文不是法律意见。
- “底层支持”不等于“播放器兼容”。尤其 WAV 的 RIFF INFO、ID3 chunk 和封面兼容性需要独立样本测试。
- 通用 PropertyMap 无法完整表达所有格式专有帧，例如复杂的同步歌词、多个语言/描述的歌词帧和私有帧。
- 库直接对给定路径执行保存，不提供本项目所需的跨标签与封面的文件事务。

因此本项目不会让业务层直接调用 go-taglib，而是实现 `internal/tags/taglibwasm` 适配器，并在其外增加安全写入协调器。

### 4.2 备选与辅助

| 方案 | 结论 |
|---|---|
| `github.com/dhowden/tag` | 读取成熟，但定位主要是解析，不满足统一写入 |
| `github.com/bogem/id3v2` | MP3/ID3 写入可用，但不能覆盖 FLAC/WAV |
| `github.com/cabbagekobe/tunetag` | 纯 Go 且格式广，但截至调研时仍非常新，适合后续做对照引擎 |
| 原生 TagLib + CGO | 能力强，但破坏简单交叉编译和单文件部署体验 |
| FFmpeg/ffprobe | 适合诊断、转码和独立验证，不作为核心写标签引擎 |
| Mutagen sidecar | 兼容性好，但会重新引入 Python 运行时，不符合项目目标 |

## 5. 其他标签工具带来的产品结论

### 5.1 Picard

Picard 的核心工作流是 cluster/lookup/scan → 检查匹配 → save。它证明“识别”和“写入”应是两个明显阶段。WAV 也需要特殊提示：Picard 文档说明 WAV 中的 ID3v2 并非所有软件都支持。

### 5.2 beets

[beets Auto-Tagger](https://github.com/beetbox/beets/blob/master/docs/guides/tagger.rst) 使用候选距离和 strong recommendation threshold，并把封面、歌词、风格和指纹交给可选插件。可借鉴：

- 数据源按能力扩展，不要求每个源提供所有字段。
- 匹配结果必须显示差异和置信度。
- 大曲库应该按小批次审核。
- 自动补全只填缺失字段和强制覆盖必须是不同策略。

### 5.3 id3tag

[id3tag](https://github.com/sysgc/id3tag) 的价值在于“每次写入都先审核，并在写入后重新读取文件验证”。本项目沿用这两个原则，但会再增加临时副本原子替换和标签级历史。

## 6. 产品边界

### 6.1 MVP 必须完成

- 配置一个或多个受控音乐根目录。
- 扫描、增量对账、浏览、搜索和筛选文件。
- MP3、FLAC、WAV 的常用标签、技术属性、歌词和封面读取。
- 单文件编辑，字段级校验、差异预览和安全写回。
- 多选批量修改与批量抓取，提供持久化任务进度。
- MusicBrainz + Cover Art Archive、LRCLIB。
- Apple Music 正式策略接口；无开发者凭据时可选 iTunes Search 作为低门槛目录搜索，但必须遵守其内容使用条款。
- 网易云、酷我策略接口和实验性实现，单源失败不能影响其他来源。
- 操作历史、失败详情和重新执行。
- 单二进制生产构建与 Linux amd64/arm64 交叉编译。

### 6.2 明确不进入 MVP

- 下载音乐音频、破解会员内容或跨平台音源替换。
- 转码、CUE 整轨切分、ReplayGain 分析。
- 自动移动/整理目录和批量重命名。
- Subsonic 服务、完整播放器、歌单和播放统计。
- AI 生成元数据或翻译歌词。
- 多租户、公开互联网 SaaS。
- 自动无确认地覆盖整座曲库。
- 内建 Chromaprint；MVP 仅预留 FingerprintMatcher 能力。

这些功能以后可以增量加入，但不应挤占“正确读取、正确匹配、安全写入”三条主链路。

## 7. 数据源与合规边界

- [MusicBrainz API](https://musicbrainz.org/doc/MusicBrainz_API) 要求正确 User-Agent 且每个客户端不超过每秒一次请求。
- [Cover Art Archive API](https://musicbrainz.org/doc/Cover_Art_Archive/API) 可按 release/release-group 查询图片，但图片本身仍可能受版权保护。
- [AcoustID](https://acoustid.org/webservice) 非商业免费服务限制为每秒不超过三次；商业使用需要单独安排。
- [Apple Music API](https://developer.apple.com/documentation/applemusicapi) 需要开发者 token；[token 文档](https://developer.apple.com/documentation/AppleMusicAPI/generating-developer-tokens) 说明需要 MusicKit identifier、私钥和 ES256 JWT。
- [iTunes Search API](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/iTuneSearchAPI/) 对封面和预览等 promotional content 有明确使用条件，因此不能默认把其封面永久嵌入本地文件。
- [LRCLIB API](https://lrclib.net/docs) 无需 key，但要求标识客户端、尊重 429/Retry-After，并建议批量请求间隔 200–500ms。
- 网易云、酷我等目前依赖非官方接口，可能随时失效，也可能受平台条款限制。实现应默认关闭、标记“实验性”，由用户主动启用，不承诺稳定性。
- 本项目只处理用户已有的本地音频，不实现音频下载。抓取结果保留来源和外部 ID，便于用户判断用途。

## 8. 最终结论

这个项目不应做成“music-tag-web 的 Go 翻译版”，而应围绕同一核心目标重新设计：

1. 用 Navidrome 式增量扫描维护可靠索引。
2. 用 TagLib-WASM 获得单二进制下的广格式读写能力。
3. 用 beets/Picard 式候选、差异和置信度控制自动化。
4. 用 id3tag 式人工确认和写后重读，再叠加原子替换与历史记录。
5. 用能力型策略接口隔离外部数据源和不稳定平台。

这条路线能先交付一个可信赖的音乐文件编辑器，再逐步扩展“智能刮削”和更多格式，而不会让高风险自动化拖垮基础能力。
