# 69 · 曲目服务端分页与页面状态恢复

> 状态：已实现  
> 更新日期：2026-08-21

## 背景

此前打开曲库页会把整座索引交给浏览器，再由前端完成搜索、目录、健康状态、格式和排序过滤。曲目数量较大时，首屏等待、JSON 传输和浏览器内存都会随曲库线性增长；从任务或设置页返回时也会重新从第一页开始。

## 实现内容

### Go 服务端

- `internal/library` 增加统一 `TrackQuery`、`TrackPage` 和不透明游标模型。
- 按 `album`、`title`、`modified`、`format` 建立稳定排序快照；相同排序键使用相对路径和 ID 作为最终 tie-breaker，避免分页重复或遗漏。
- 默认页大小为 100，最大 200。游标携带查询哈希和索引版本；扫描、单曲回读、写入、缺失清理和切换曲库都会使旧游标失效。
- `GET /api/v1/tracks` 在服务端执行关键词、目录 ID/路径、递归目录、健康状态、格式和排序，返回 `tracks`、`total`、`nextCursor` 和 `hasMore`。
- 新增 `POST /api/v1/tracks/resolve`：按 ID 或查询结果解析曲目，单次最多 1000 首；超限返回 `track_selection_too_large`，避免批量操作绕过安全上限。

### 前端

- `LibraryPage` 只持有当前查询已经加载的页面，搜索采用约 250ms 防抖并取消过期请求；目录、递归、状态、格式和排序变化会重新请求第一页。
- `TrackList` 使用 `Virtuoso.endReached` 追加页面，底部显示继续加载/加载中状态，工作区底栏显示“已加载 X / 共 Y 首”。
- 新增模块级 `LibraryViewCache`。曲库页卸载前保存已加载曲目、游标、筛选、选中 ID、当前曲目和 `Virtuoso` `StateSnapshot`；重新挂载先显示缓存，再后台刷新第一页。
- 浏览器 `localStorage` 只保存曲库对应的轻量查询条件和 `scrollTop`，整页刷新后按游标重新请求数据，不把大量曲目写进本地存储。游标失效时保留当前界面并从第一页安全重建。
- “全选”解析当前服务端结果集，不局限于已加载页；批量补全、批量编辑和标签快照继续受 1000 首上限保护。
- `ReviewPage` 和 `JobsPage` 不再读取整座曲库，改为按任务项/曲目 ID调用解析接口。

## 使用约定

- 默认排序和排序方向保持现有曲库页行为。
- 分页游标只由服务端生成，客户端不解析其内容。
- 批量匹配、编辑和快照操作单次最多 1000 首；结果超过上限时应先缩小搜索、目录或筛选范围。
