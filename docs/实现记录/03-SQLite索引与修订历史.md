# SQLite 索引与修订历史验证

验证日期：2026-08-20

## 本轮完成内容

- 使用 `modernc.org/sqlite`，保持 CGO-free 和单二进制构建。
- 使用 `pressly/goose/v3` 管理 SQL migration，并通过 `go:embed` 把 migration 编入二进制。
- 新增 `--data-dir` / `TAGGER_DATA_DIR`，默认在 `./data/tagger.db` 保存运行时状态。
- SQLite 启用 foreign key、5 秒 busy timeout、WAL journal 和 `synchronous=NORMAL`。
- 每次扫描在一个事务内更新曲库摘要和曲目快照，并用 scan token 删除已不存在的曲目。
- 服务启动时优先恢复同一音乐根目录最近一次持久化索引；用户触发重新扫描后再用磁盘事实覆盖索引。
- 每次安全标签写入成功并重新索引后，记录写入前后 revision、字段 diff、原始标签快照、来源和时间；候选采用只提交 provider ID，由后端注册表反查可信来源名称。
- 新增修订列表与详情 API：`GET /api/v1/revisions`、`GET /api/v1/revisions/:id`。
- 前端历史页读取真实 API，展示真实前后值、修订数量、搜索、空状态和错误状态。

## 写入与历史的一致性边界

当前顺序是：

1. 在同目录临时副本上修改标签。
2. 重读临时副本并验证目标字段。
3. 原子替换音乐文件并同步目录。
4. 重新扫描并持久化当前曲目快照。
5. 追加标签级修订记录。

音乐文件是最终事实源，SQLite 不参与文件原子替换。若第 5 步失败，API 会把“修订历史写入失败”加入 warnings，但不会把已成功写入的音乐文件误报为失败。下一阶段会加入扫描检测外部变化和恢复流程，进一步覆盖文件成功/数据库失败后的修复路径。

历史保存的是标签级快照，不是整首音频的位级备份。用户仍应使用 NAS 快照或独立备份保护音乐文件。

## 自动化验证

SQLite 测试覆盖：

- 首次启动自动 migration，foreign key 与 WAL 配置生效。
- 扫描结果写入/读取、第二次扫描删除陈旧曲目。
- 关闭并重新打开数据库后，曲库索引和完整修订快照仍存在。
- 并发追加修订记录，并按时间倒序限制返回数量。
- 曲库服务首次扫描后持久化；第二次构造服务直接恢复索引；显式重新扫描才再次读取音乐文件。
- 修订列表、详情和 404 API 行为。
- 使用 `TestMusic` 的 MP3 临时副本走完整 API 写入，验证真实 TagLib-WASM 修改、重新索引、字段 diff、数据库重开后历史仍存在。原始测试音乐未被修改。

前端测试覆盖真实修订 API 的 envelope 解包和稳定路径；历史页继续复用应用级导航测试。全量 Go 测试、前端类型检查和前端测试均纳入本轮验收。

生产单二进制还执行了独立进程验收：临时复制一首 MP3，启动服务后通过 HTTP API 采用 `MusicBrainz` 来源修改标题，确认历史中的 action、source 和真实 diff；关闭进程并使用同一数据目录重启后，曲目 revision 和修订记录均恢复。浏览器检查了历史列表、详情 diff、动态计数和搜索空状态。验收前后原始 `TestMusic` 文件 SHA-256 一致，临时目录随后清理。
