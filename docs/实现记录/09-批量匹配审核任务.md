# 批量匹配与审核任务

验证日期：2026-08-20

## 持久化模型

Migration v4 为 job 增加 `payload_json`，新增 `match_items`：每个 item 关联 job/track，保存候选 JSON、状态、错误和更新时间。候选 JSON 只返回规范化字段，不包含 provider 原始封面 URL；服务重启后 Registry 从 SQLite cache 恢复 URL 引用，仍能安全应用候选封面。

`match` worker 对每首曲目独立查询 Provider：单曲失败写入 item error 并继续下一首；只要至少一首存在候选，所有候选分析完成后 job 进入 `review`，失败/无匹配项保留逐项错误，不会阻止成功项审核，也不会把“找到候选”误报为已写入文件。全部曲目均失败或无匹配时进入 `failed`，仍可从任务中心打开审核并逐曲重新匹配。

新增 API：

- `POST /api/v1/matches/tracks/batch`：提交 track IDs 和 provider IDs，返回 202/job。
- `GET /api/v1/jobs/:id/matches`：读取持久化审核项与候选。

## 前端

真实模式下 Review 页面会创建批量 match job；新任务进入任务中心显示抓取进度，`review` 或 `failed` 终态可重新打开并加载真实候选。Mock 模式继续使用本地 fixture，便于无后端开发。候选来源、分数、字段 diff 和审核状态沿用原型交互。

真实模式不会在后端无候选时回退到 mock 数据：`no_match`/`failed` item 会显示为“未找到匹配”并安全跳过。审核页的字段 checkbox 已提升为页面状态，提交写入任务时只发送仍被勾选的标准字段；显式空数组会生成 no-op patch，不会意外恢复为全字段写入。

## 验收

- TestMusic 两首真实曲目使用 Apple 查询，job 进入 `review`，2/2 item 各有 2 个候选；最佳候选分数分别为 0.94 和 0.89。
- 关闭并重启服务后，`GET /jobs/:id/matches` 仍返回 2 个候选项；任务事件断线后由 GET 快照恢复。
- Store、Server 和前端 API 测试覆盖 migration、候选 JSON、202 入队、列表读取和 URL encoding。

审核选择已经提交为 `write` job，每个 item 使用当前 revision 做安全写入与部分成功审计；失败 item 可从任务中心单独重试。
