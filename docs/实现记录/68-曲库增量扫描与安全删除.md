# 曲库增量扫描与安全删除

## 背景

此前“重新扫描”会遍历整座曲库并重新读取所有音频标签。批量标签/封面写入结束后也会触发整库扫描；新增曲库时目录探测和首轮扫描还会重复遍历。多曲库场景下，曲目 ID 只由相对路径生成，两个曲库出现同名相对路径时存在互相覆盖风险。

## 扫描行为

- `full`：完整遍历并重新读取所有音频，用于首次建立索引和显式维护。
- `quick`：遍历文件系统元数据，比较音频与同名 `.lrc` 的大小/mtime 指纹，只读取新增或发生变化的文件。
- `targeted`：文件系统监听将变化合并到受影响目录，只扫描这些目录；目录外的索引保持不变。
- 批量安全写入和批量编辑完成后调用批量精准回读，不再触发整库标签读取。
- 完整扫描和快速扫描都不会因为单个目录读取失败而清理未覆盖范围；缺失文件保留在索引中并标记为“文件缺失”。

## 文件监听

当前活动曲库使用 fsnotify 递归监听。事件在默认 5 秒窗口内按目录去重后先做轻量文件清单对账，再排队 targeted 元数据扫描；等待时间可通过 `--watcher-wait` / `TAGGER_WATCHER_WAIT` 调整（`0–10m`）。写入或扫描任务繁忙时，受影响目录批次不会丢弃，而是等待任务空闲后自动重试；纯待审核状态不再阻塞文件变化。对于不支持事件监听的文件系统，可使用 `--watch-mode poll` 进行当前目录轮询，或通过 `--reconcile-interval` / `TAGGER_RECONCILE_INTERVAL` 开启低频 quick 全库对账。隐藏目录、系统目录、隐藏临时文件和符号链接沿用扫描器的忽略边界。

## SQLite 迁移

`00013_incremental_library.sql` 将 `tracks` 的主键作用域改为 `(library_id, id)`，增加文件指纹和缺失状态字段，并为匹配查询历史补充 `library_id`。增量保存只更新变化曲目和当前曲库摘要，完整保存仍使用原子快照替换逻辑。

## 删除边界

`DELETE /api/v1/libraries/:id` 只允许删除非活动曲库，并要求没有运行中或待审核任务。事务清理该曲库的曲目、扫描/匹配/写入任务、候选、查询历史、修订历史和不再引用的 artwork blob。Provider 公共缓存不按曲库删除。

删除实现没有调用文件删除 API，也不接收需要删除的本地路径。集成测试在音乐目录中写入哨兵文件，删除后校验文件仍存在且内容不变。

`POST /api/v1/libraries/:id/missing/purge` 是独立的确认动作，用于清理已标记缺失的索引，并回收因此变成无引用的历史封面 blob；默认扫描不会自动清理。

## 前端变化

- 移除原先禁用的“扫描模式 / 定时对账 / 符号链接”占位下拉框。
- 设置页显示真实的自动监听、快速扫描和完整扫描策略。
- “重新扫描”默认为快速扫描，另提供“完整扫描”和“清理缺失索引”。
- 已注册的非活动曲库提供删除按钮，并在确认文案中明确“不会删除本地音乐文件”。

## 验证

- Go：scanner、library、store、server、watcher 和 cmd/tagger 测试通过。
- 新增快速扫描未变化文件读取次数、缺失标记、相同相对路径隔离、删除本地文件安全边界和 watcher debounce 测试。
- 前端：Vitest 全量测试通过（113 tests）。
