# 批量候选封面与持久化引用

验证日期：2026-08-20

## 批量审核流程

Review 页面默认不采用候选封面，用户必须显式勾选“封面”。写入任务的每个 item 携带 `artwork: true`，后端不会信任客户端提交的远程 URL，而是从已持久化的 match candidate 和 Provider Registry 反查封面引用。

worker 的顺序是：

1. 反查并下载候选封面，执行 Provider 域名、HTTPS、DNS 公网地址、大小、MIME 和图片解码校验。
2. 使用原有 base revision 写入标准标签。
3. 以标签写入后的新 revision 写入嵌入封面。
4. 重新扫描并把标签 diff、封面 diff、前后 raw tags 合并到同一条 revision 审计。

如果标签已经成功但封面写入失败，match item 状态为 `artwork_failed`；重试接口会读取当前曲目 revision，发送空字段集合，只补写封面，避免重复标签覆盖或 revision 冲突。

## 引用持久化

Migration v5 新增 `provider_artwork_refs`，以 candidate ID 保存 Provider、HTTPS URL 和 30 分钟 TTL。Provider Registry 启动时恢复未过期引用并清理过期记录，因此服务重启后，已经持久化的批量审核候选仍可以应用封面。URL 仍只作为后端短期引用，最终下载入口继续执行完整安全校验。

## 测试

- Store 测试覆盖封面引用保存、读取和 TTL 清理。
- Registry 测试覆盖缓存与设置重启后，封面引用在首次重新搜索前也可读取。
- Server 测试覆盖 `artwork_failed` 重试时改用当前 revision、清空字段并保留 artwork 选项。
- 标准 MP3/FLAC/WAV 封面原子写入和服务端 Provider 封面安全校验继续由现有 TestMusic 集成测试覆盖。

## 当前边界

批量封面与标签目前在同一 item 内顺序执行，TagLib-WASM 没有跨两种变更的事务接口；封面失败会保留已成功的标签并生成审计，随后只重试封面。后续可增加预览阶段的图片下载缓存和更细粒度 item 事件。
