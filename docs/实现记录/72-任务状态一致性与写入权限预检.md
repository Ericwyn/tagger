# 任务状态一致性与写入权限预检

## 问题与根因

部署实例中出现过安全写入任务显示“已处理 8 / 8、成功 0、失败 8”，但状态仍是“部分完成”，详情同时写成“已写入 8/8”。逐项错误表明 8 首都在创建音乐文件同目录临时副本时收到 `permission denied`。

这是两个独立问题：

- 旧任务管理器只要 `failed > 0` 就写入 `partial`，没有区分混合结果和全部失败；完成时还会重算计数，可能掩盖 worker 的真实快照。
- 写入详情把循环位置 `index + 1` 直接描述为“已写入”，混淆了已处理和成功。扫描器中的权限位提示也不能代替容器进程对挂载目录的有效权限。

安全 writer 使用同目录临时副本、写后校验和原子重命名，因此运行 Tagger 的进程必须能读取源文件，并能在每个目标文件的父目录创建和删除临时文件。仅让音乐文件本身显示可写，或只让曲库根目录可写，都不足以保证子目录能够安全写入。

## 实现

- 任务终态统一为：全部成功 `succeeded`；成功和失败并存 `partial`；零成功且存在失败 `failed`；匹配任务有任意成功候选时进入 `review` 并保留失败项。
- Manager 校验 `0 <= succeeded + failed <= processed <= total`，正常完成还要求 `succeeded + failed == processed == total`，不再在终态阶段伪造或覆盖 worker 计数。
- 写入和批量编辑进度统一显示“已处理 / 成功 / 失败”，100% 明确标注为处理进度，不再代表成功率。
- migration `00016_job_state_consistency.sql` 将历史上 `partial + succeeded=0 + failed>0` 的任务修复为 `failed`。
- 写入和批量编辑 API 在入队前按目录去重执行权限预检：读取源文件，并真实创建、关闭和删除短生命周期同级探测文件。预检失败返回 `422 write_target_unwritable`，提示检查只读挂载及容器 UID/GID，不修改审核项状态，也不创建任务。
- 标签成功但后续封面失败时，“已经发生的文件变更”与“item 整体成功”分开统计；文件仍会重新索引并保留历史，但计数只记录一次失败。
- 失败/部分完成的匹配流程仍可打开审核、重新匹配和再次写入；重试会包含取消前缺失或仍为 pending 的 item，并把任务总数改为实际重试项数。

## 验证

- Go 回归覆盖全失败、混合结果、审核混合结果、提前结束、过滤重试总数、取消后的缺失/pending item、历史状态迁移、同目录权限探测，以及匹配/批量编辑 API 入队前拒绝不可写目录。
- React 回归覆盖全失败任务的状态与处理进度标签，以及失败匹配任务重新打开审核。
- `go test ./...`、`go vet ./...`、`go build ./...` 通过；任务相关路径通过 `go test -race ./internal/jobs ./internal/server ./cmd/tagger`。
- 前端 128 个 Vitest 用例、TypeScript 检查和 Vite 生产构建通过。
